# Build / signing separation

Repo: `shiba-meta-secure-boot` (all paths below are relative to that layer).

`SHIBA_SIGN_MODE` (defined in `conf/shiba-signing.inc`) decides
whether the machine running bitbake holds the signing private keys.

| Mode | Private keys | TF-A `.stm32` | FIP | Kernel FIT | SWU |
|---|---|---|---|---|---|
| `full` (default) | required | header signed, `_Signed` | CoT certs, `_Signed` | signed | CMS signed |
| `unsigned` | none needed | header signature zero | no CoT certs | signature node, empty value | no `sw-description.sig` |

**The binaries themselves are identical in both modes.** `unsigned` does not
build a different, weaker product: TF-A still gets `TRUSTED_BOARD_BOOT` and
`MEASURED_BOOT`, the FIP is assembled from the same inputs, the rootfs and the
FIT payload are the same bytes. Only the four key-consuming steps are left
undone, each in a form that can be completed later from the artifact alone.

`unsigned` images **do not boot** on a secure-boot device. They are the input to
a signing machine that has the keys and the binaries — but no source tree.

> `SIGN_ENABLE = 0` is **not** how this is done, and must not be reintroduced.
> In meta-st that switch also drops `TRUSTED_BOARD_BOOT` and mbedtls, and with
> them our `MEASURED_BOOT`. Measured on a real build, the resulting BL2 has
> **0 mbedtls symbols (vs 4) and 4 measured-boot strings (vs 35)** — it can
> neither authenticate the FIP nor extend the PCRs, so the TPM-sealed LUKS keys
> would never unseal. Signing that image afterwards yields a signed binary with
> no chain of trust.

## What still has to be decided before the build

Public material is embedded into the images and cannot be swapped afterwards:

| Material | Variable | Ends up in |
|---|---|---|
| FIT verification public key | `${UBOOT_SIGN_PUBKEY_DIR}/${UBOOT_SIGN_KEYNAME}.crt` | the FIP's `HW_CONFIG` (`u-boot-<dt>-<type>.dtb`) |
| SWU verification certificate | `SWU_SIGN_CERT` | rootfs (**dm-verity protected**) |
| ST ROT public key hash | — | device OTP fuses, not in any image |

Replacing the SWU certificate after the build changes the rootfs, which changes
the dm-verity root hash, which changes `dm-verity.env` in the initramfs, which
forces the fitImage to be regenerated and re-signed and the bootfs image to be
rebuilt. In practice that is a full rebuild, so **the SWU certificate is fixed at
build time.**

## Workflow

Set `SHIBA_SIGN_MODE` in `local.conf` (a plain `?=` in the layer, so a hard
assignment in `local.conf` wins; no environment passthrough needed), point
`SIGN_KEY_PATH` at a public-only directory, and build in three steps:

```bash
./run bitbake                                    # 1) the image
./run gen-swu                                    # 2) the .swu
bitbake -c prepare_sign_bundle st-image-secure   # 3) the sign bundle
```

The order matters. `swu-image-secure` is written to run *after* the image build
and reads its inputs from `DEPLOY_DIR_IMAGE`; declaring those as dependencies
would make `bitbake swu-image-secure` walk the whole image graph — measured:
12777 tasks, re-running `st-swu-partition:do_rootfs`. Instead the precondition is
checked and each step says what to run first if something is missing.

Step 3 produces `${DEPLOY_DIR_IMAGE}/sign-bundle/` and a tarball beside it:

```
sign-bundle/
  sign.sh          signing + re-assembly; lives in the layer, so it is reviewed
                   and versioned like any other source
  bundle.conf      artifact names, generated by the build -- the script cannot
                   drift away from what was actually produced
  README.txt
  MANIFEST.sha256
  tools/           cert_create, fiptool, uboot-mkimage, uboot-fit_check_sign,
                   debugfs, dumpe2fs, e2fsck, and lib/ -- the loader and every
                   shared library they need
  pubkeys/         the public material this build embedded
  unsigned/        the artifacts to sign
  flashlayout/     .tsv templates
```

## What the signing machine does

It needs the bundle, the private keys and `STM32MP_SigningTool_CLI` — no source
tree, no sstate, no bitbake.

```bash
./sign.sh --keys <dir> [--sign-tool <path>] [--out <dir>] [--skip-swu]
```

| # | Artifact | Step |
|---|---|---|
| 1 | `tf-a-*.stm32` | `STM32MP_SigningTool_CLI` fills in the zeroed header signature fields; the payload is untouched |
| 2 | `fip-*.bin` | `fiptool unpack` → `cert_create` → `fiptool create`; unpack returns the payloads byte-identically, named after the very `cert_create`/`fiptool` options |
| 3 | U-Boot control FDT | nothing — `fdt_add_pubkey` already embedded the FIT verification key into the FIP's `HW_CONFIG` (`UBOOT_CONTROL_DTB` in `bundle.conf`), **not** `u-boot.dtb` |
| 4 | `fitImage` | `mkimage -F -k`, verified against that same control FDT, then written back into the bootfs ext4 with `debugfs` |
| 5 | `images/` + `.tsv` | the signed set, and flashlayout entries repointed at the signed names |
| 6 | `.swu` | every `/shiba` member replaced from the signed `images/` set, `sw-description`'s `sha256` updated, CMS re-signed and verified, cpio repacked, and republished as `swupdate/swu-image-secure-<machine>-<version>.swu` — the same versioned name the build's `do_deploy_swu` publishes |

Results land in `signed/`.

## Key material layout

`SIGN_KEY_PATH` currently holds private and public material together. Two
variables allow splitting them so a build machine can mount a public-only tier:

- `SIGN_PUBKEY_PATH` → defaults to `SIGN_KEY_PATH`; `UBOOT_SIGN_PUBKEY_DIR`
  derives from it and must contain `uboot-sign-key.crt`.
- `SWU_SIGN_CERT` → defaults to `${SWU_SIGN_KEY_DIR}/swu-sign-cert.pem`.

Private material used only in `full` mode: `privateKey.pem`, `pass`,
`uboot-sign-key.key`, `uboot-sign-img-key.key`, `${SWU_SIGN_KEY}`.

## Implementation notes

- **`FIT_GENERATE_KEYS`** follows the mode. Left at `1` without a key, bitbake
  silently fabricates a throwaway signing key and embeds its public half in
  the control FDT — an "unsigned" build would quietly become a build signed by a
  garbage key.
- **`UBOOT_SIGN_ENABLE` stays `1` in both modes.** `mkimage -F -k` fills in an
  existing signature node; it cannot create one. Turning it off would leave the
  FIT with no signature node for the signing machine to fill.
- **`fdt_add_pubkey`** replaces `mkimage -f auto-conf -K` in unsigned mode; it
  embeds the key from the certificate alone. It is not installed by oe-core's
  `u-boot-tools`, so `recipes-bsp/u-boot/u-boot-tools_%.bbappend`
  adds it.
- **U-Boot's control FDT is the FIP's `HW_CONFIG`, not `${UBOOT_DTB_BINARY}`.**
  meta-st inserts the FIT verification key itself, in `export_binaries()`, by
  running `${UBOOT_MKIMAGE_SIGN} -K` on `${B}/<config>/u-boot-<dt>-<type>.dtb` —
  a different file from `u-boot.dtb`, which on this platform never reaches the
  device. Pointing `UBOOT_MKIMAGE_SIGN` at the no-op stand-in therefore removed
  the key from the product entirely: the FIP shipped a U-Boot that could not
  verify any FIT. Confirmed on hardware — the boot log showed only
  `Verifying Hash Integrity ... sha256+ sha384+`, and the FIP's `HW_CONFIG` had
  no `key-uboot-sign-key` node at all. The key-free build now inserts it in
  `do_compile:append` with `fdt_add_pubkey -r conf`, before either `do_deploy`
  or the sysroot populate copies those files out (the sysroot pass asks
  `export_binaries` not to sign, so patching the build tree covers both).
  A signing build is unaffected: meta-st's own path already produces
  `required = "conf"` there, verified against an existing release build.
- **`CONFIG_LEGACY_IMAGE_FORMAT` bypassed that enforcement.** The boot command is
  `bootm <addr>` on whatever sits at `/fitImage`, and `bootm` picks the format
  from the blob's magic — a legacy uImage there boots with no signature check,
  never entering the FIT path. Upstream disables the legacy format once
  `FIT_SIGNATURE` is set, precisely "so that unsigned images cannot be loaded";
  ST's `stm32mp15_defconfig` turns it back on. Disabled in
  `files/uboot_fragment.cfg`.
- **`UBOOT_MKIMAGE_SIGN`** points at `files/shiba-mkimage-nosign` in unsigned
  mode, which neutralises the oe-core FIT signing step without forking
  `kernel-fitimage.bbclass`.
- **`SIGN_ENABLE` stays `1` in both modes**; only two invocations are replaced.
  `files/shiba-sign-tool-nosign` stands in for `SIGN_TOOL` (copies `-bin` to
  `-o`, leaving the STM32 header signature fields zero) and
  `files/shiba-fip-nosign` wraps `create_st_fip_binary.sh`, dropping
  `--sign/--signature-key/--signature-key-pass`. Both keep every other build
  flag — `TRUSTED_BOARD_BOOT`, mbedtls, `MEASURED_BOOT` — intact.
- **`SIGN_KEY_PASS` cannot be empty.** meta-st's `init_keylist_from()` calls
  `bb.fatal` on an empty value, so the key-free build passes a placeholder that
  the stand-in tool ignores.
- **Artifact names lose `_Signed` in unsigned mode** even though `SIGN_ENABLE=1`,
  because `TF_A_SIGN_SUFFIX` / `FIP_SIGN_SUFFIX` / `FLASHLAYOUT_SUFFIX` are set
  from `SHIBA_SIGN_MODE` instead. That matches what `create_st_fip_binary.sh`
  does on its own once `--sign` is gone, and keeps the names truthful.
- **A python `:prepend` must never `return` early.** bitbake splices it into the
  task's own function body, so `return` aborts the whole task. An early return
  in `do_swuimage:prepend` silently skipped the entire `.swu` generation —
  `do_deploy_swu` still created the symlink, leaving a dangling link and no
  package. Branch with `if/else` instead.
- **`do_deploy_swu` had no ordering at all.** It was declared `after
  do_image_complete`, but this recipe inherits `swupdate` (not `swupdate-image`)
  and has no such task, so the constraint was vacuous — on a clean tree it ran as
  task 19 of 12777 and failed on a missing `version.txt`. It is now `after
  do_swuimage`, which is intra-recipe and so pulls in nothing. The missing
  cross-recipe dependencies are deliberately **not** declared; see the workflow
  above.
- **`/shiba` must be refreshed whole, not just the signed pieces.** `prepare-swu`
  fills it from `images/`, written by `do_install_secure_images` — a task that
  `-c prepare_sign_bundle` does not pull in, so `images/` (and the SWU partition
  built from it) can lag behind the deploy directory the bundle takes its
  artifacts from. Replacing only the bootfs put a current kernel/initramfs, whose
  dm-verity root hash is current, on top of an hour-old rootfs image; the device
  flashed and booted fine and then died on the *updated* bank with
  `device-mapper: verity: metadata block 209693 is corrupted`. `sign.sh` now
  overwrites all of `/shiba` from `signed/images/` and refuses to run if the two
  sets do not correspond one for one.
- **`GENERATE_COT=1`** in the TF-A bbappend does not generate certificates:
  meta-st builds TF-A with `TF_A_CONFIG_MAKE_TARGET = "all"`, never `fip`, so
  `certificates` is never a dependency. The Chain-of-Trust certificates come from
  `create_st_fip_binary.sh`, which passes `privateKey.pem` to `cert_create` as
  `--rot-key`. `ROT_KEY` is correctly unset.

## Verified

Run end to end on 2026-08-27 across two machines: an Ubuntu 22.04 build host
holding **no private key at all**, and a **Debian 12** signing host with no build
tree, using a key set generated on the signing host. Both positive and negative
controls passed:

| Check | With the signing host's key | With a different key |
|---|---|---|
| TF-A header's embedded ECDSA public key | byte-identical to `publicKey.pem` | — |
| FIP `trusted-key-cert` signature | `Verified OK` | `Verification failure` |
| Kernel FIT (`fit_check_sign -k` the key-free build's control FDT) | `Signature check OK` | — |
| SWU CMS signature | `CMS Verification successful` | `certificate verify error` |

The FIT result is the one that matters most: the public key a key-free build
embedded from a certificate alone validates a signature made later with the
private key.

A full runbook — machine setup, key generation, every command, and the traps hit
along the way — is kept outside this repository.

## Open items

- **HSM / PKCS#11 is available.** `STM32MP_SigningTool_CLI` takes `--module`,
  `--slot-index`, `--key-index` and `--active-keyIndex`; `cert_create --rot-key`
  accepts a PKCS#11 URI; `mkimage` has `-N <engine>`. Keeping the private keys in
  an HSM is therefore a real alternative to splitting the machines, and worth
  weighing against this bundle.
